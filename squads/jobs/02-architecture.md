# Architecture: job search

> Squad plan. Folders, chain, data contracts, filter rules, direct consultation and the squad's `AGENTS.md`.
> The `{{...}}` variables come from `user/profile.md` and `projects/jobs/jobs-profile.yaml`.

## 1. Folder `{{ROOT}}/projects/jobs/`

```text
{{ROOT}}/projects/jobs/
├── AGENTS.md                      # squad rules (§6)
├── squad.yaml                     # filled-in manifest (read by registry.py)
├── jobs-profile.yaml              # what the user is looking for
├── achievements.yaml              # what they can prove (source of truth)
├── application-data.yaml          # answers for forms (sensitive, in .gitignore)
├── evidence/                      # current CV, screenshots, certificates
├── templates/
│   ├── cv-ats/                    # one column, no icons, selectable text
│   └── cv-custom/                 # optional: the user's own design
├── scripts/                       # start_search.sh, deliver.py, render_cv.py, check_links.py
├── skills/                        # the specialists' skills (one folder per skill)
│   └── orchestration/             # orchestration-jobs only (the orchestrator reads this folder)
├── companies/<company>.md         # company profiles, reusable for 30 days
├── searches/YYYY-MM-DD-HH.md      # result of each search
├── openings/
│   └── JOB-YYYYMMDD-company-role/
│       ├── opening.md             # scout
│       ├── status.json            # status and history; updated by whoever acts
│       ├── analysis.json          # analyst
│       ├── application/           # writer (+ render files) and applier (submission.json, screenshots)
│       ├── review-N.json          # reviewer (one per round)
│       └── interview.md           # writer, interview mode
├── outbox/
│   ├── ready/<ID>.json            # approved, waiting for the delivery script
│   ├── sent/<ID>.json             # already delivered to the user
│   └── PAUSE                      # if it exists, no searches are launched
└── tracking.csv                   # view of all openings; regenerated by deliver.py
```

Opening ID: `JOB-YYYYMMDD-<company>-<role>` in lowercase, without accents, at most 50 characters. E.g.: `JOB-20260925-acme-data-analyst`.

## 2. Automatic chain

```text
cron (search_times) ── start_search.sh ──► task "Search <date>"
                                                 │
scout ── searches, saves opening.md, filters ────┤ for each PASS (up to the daily quota):
                                                 ▼ creates the analyst's task
analyst ── analysis.json ────────────────────────┤ PURSUE and score ≥ apply_threshold:
                                                 ▼ creates the writer's task
writer ── application/ (CV, PDF, DOCX…) ─────────┤ always: creates the reviewer's task
                                                 ▼
reviewer ── review-N.json ──┬─ APPROVED ──► outbox/ready/<ID>.json
                            ├─ FIX, round 1 ──► creates the writer's task with corrections
                            │                   (the writer creates the reviewer's task again, round 2)
                            └─ not approved in round 2 ──► status not_approved (goes to the weekly summary)

cron every 15 min ── deliver.py ──► message to the user: link + attached CV
                                    (only within the user's schedule; also reports blocked tasks)
```

What the user receives for each approved opening:

```text
🟢 84/100 · Data analyst — Acme (remote in the region)
Apply: https://boards.greenhouse.io/acme/jobs/123
CV attached 📎 cv_ats.pdf
Reply: "apply" · "change: <what>" · "no"
JOB-20260925-acme-data-analyst
```

Warnings (for example "interview probably in English") add one line. Nothing else: no analysis, no intermediate steps.

### User replies

```text
"apply"          → orchestrator ──► applier ──┬─ simple form ──► fills it in, uploads the CV, submits
                                              │                  → "✅ Applied" + screenshot
                                              ├─ missing data ──► asks you (buttons) and continues
                                              └─ needs an account, CAPTCHA, email, LinkedIn…
                                                                   → "Apply here yourself" + ready answers
"change: <what>" → orchestrator ──► writer (CHANGE mode) ──► reviewer ──► new CV the same way
"no"             → status skipped (the reason, if given, improves the searches)
"I applied", "they called me", "rejected" → status updated
"prepare me for the interview with X" → writer (INTERVIEW mode) ──► interview.md
```

## 3. What is a script and what is a bot

| Piece | Type | Level |
| --- | --- | --- |
| Start the search at the set times | Script `start_search.sh` (cron `--no-agent`) | 1 |
| Search for openings on varied websites, read the text, apply the filter | Bot `jobs-scout` | 1 |
| Analyze the opening, research the company (subagent), decide the fit | Bot `jobs-analyst` | 1 |
| Write the content of the CV, cover letter, answers | Bot `jobs-writer` | 1 |
| HTML → PDF, DOCX, extracted text, mechanical ATS report | Script `render_cv.py` (run by the writer) | 1 |
| Check that the evidence links respond | Script `check_links.py` (run by the writer) | 1 |
| Review truthfulness, ATS, recruiter, hiring manager, writing | Bot `jobs-reviewer` + 5 subagents | 1 |
| Send approved work to the user and regenerate the tracking | Script `deliver.py` (cron `--no-agent`) | 1 |
| Fill in and submit application forms, with confirmation | Bot `jobs-applier` | 1 |
| Chat with the user and handle their replies | Orchestrator | 1 |
| Query job board APIs, deduplicate, normalize | Scripts `ingest_*.py` | 2 |
| Weekly summary and strategy tuning | Orchestrator agent cron | 1 (summary) · 3 (tuning) |

## 4. Filter rules (scout)

Applied in this order; the first rule that discards, discards.

1. **Scam or closed opening**: asks for payments or bank details, no identifiable company, 404 or "position closed" → `DISCARD`, with a label.
2. **Language**: normalize what the opening requires using the table below. If it exceeds `max_required_language` → `DISCARD`. If the opening is in that language and does not state a level → `FLAG` with the warning "interview probably in <language>".
3. **Geography**: residence or onsite presence outside `work_mode`/`cities`, remote restricted to another country, or a time zone outside `timezone_max_diff_h` → `DISCARD`.
4. **Role**: does not match `target_roles` or `acceptable_roles` → `DISCARD`.
5. **Seniority**: requires more than `years_experience.in_role + seniority_margin` years → `DISCARD`; between `+0` and `+margin` → `FLAG`.
6. **Contract and salary**, only if the opening states them: outside `contract` or below `min_salary` → `DISCARD`.
7. **Companies or sectors to avoid** → `DISCARD`.

If nothing discards → `PASS`. Never soften a requirement so that the opening passes.

### Language to CEFR normalization table

| Text in the opening | Assumed CEFR |
| --- | --- |
| native, nativo, bilingual, bilingüe | C2 |
| fluent, fluido, advanced, avanzado, proficient, C1, C2 | C1 |
| upper-intermediate, B2, business, professional working proficiency, "daily meetings with clients" | B2 |
| intermediate, intermedio, conversational, B1, "reading documentation" | B1 |
| basic, básico, elementary, A1, A2, "nice to have" | A2 |
| opening in that language with no stated level | unknown → FLAG |
| opening in the user's native language with no mention | not required |

## 5. Data contracts

### `openings/<ID>/opening.md` (scout)

```markdown
---
id: JOB-...
company: ...
role: ...
url: ...
apply_url: ...
source: ...
posted_at: YYYY-MM-DD | unknown
work_mode: remote_global | remote_region:<region> | remote_country:<iso> | hybrid:<city> | onsite:<city> | unknown
opening_language: es | en | ...
required_language: {english: B2 | unknown | not_required}
filter: PASS | FLAG | DISCARD
filter_reasons: ["short, verifiable phrases"]
labels: ["language_not_stated", "possible_repost", ...]
---
<full text of the opening, as is>
```

### `searches/YYYY-MM-DD-HH.md` (scout)

Table with one row per opening found: `id | company | role | work mode | required language | filter | reason | url`. `PASS` rows first, then `FLAG`; `DISCARD` rows at the end, grouped by reason. At most `weekly_volume` `PASS` rows.

### `openings/<ID>/analysis.json` (analyst)

```json
{
  "id": "JOB-...",
  "opening": {"role": "", "company": "", "seniority": "", "opening_language": "", "required_language": {}, "work_mode": ""},
  "requirements": {
    "must_have": [], "nice_to_have": [], "responsibilities": [],
    "tools": [], "keywords": [], "disqualifiers": [], "priorities": []
  },
  "company": {"summary": "", "product": "", "sector": "", "brand_tone": "", "team_signals": [], "news": [], "sources": []},
  "evidence": [{"requirement": "", "achievements": ["ACH-007"], "confidence": 0.8, "note": ""}],
  "fit": {
    "score": 0, "decision": "PURSUE | WATCH | REJECT",
    "strengths": [], "gaps": [], "hard_gaps": [], "transferable": [],
    "overselling_risk": "low | medium | high", "reason": ""
  }
}
```

### `openings/<ID>/application/` (writer)

| File | Content |
| --- | --- |
| `strategy.md` | Headline, main narrative, order of experiences and skills, keywords to cover, chosen evidence pieces and why, CV language |
| `cv_content.json` | `{language, header{name, headline, links[]}, summary, experience[{title, company, dates, bullets[{text, achievements[]}]}], projects[], skills[], education[], languages[{language, level}]}`. **Each bullet cites its achievements** |
| `cover_letter.md`, `answers.md`, `recruiter_message.md` | Depending on `deliverables`. Each paragraph ends with `<!-- achievements: ACH-... -->` |
| `cv_ats.pdf`, `cv_custom.pdf`, `cv.docx`, `cv_ats.txt`, `render_report.json` | Output of `render_cv.py` |
| `links.json` | Output of `check_links.py` |

### `openings/<ID>/review-N.json` (reviewer)

```json
{
  "id": "JOB-...", "round": 1,
  "verdict": "APPROVED | FIX | HUMAN_REVIEW",
  "reviews": {
    "truthfulness":   {"verdict": "PASS | FAIL", "findings": [{"location": "", "text": "", "problem": "", "expected_achievement": ""}]},
    "ats":            {"verdict": "", "keyword_coverage": 0.0, "missing": [], "defects": []},
    "recruiter":      {"verdict": "", "seconds_to_understand": 0, "would_open_evidence": true, "blockers": []},
    "hiring_manager": {"verdict": "", "can_do_the_job": true, "concerns": [], "interview_questions": []},
    "writing":        {"verdict": "", "findings": [{"location": "", "text": "", "fix": ""}]}
  },
  "corrections": [{"type": "content | format | strategy", "instructions": ""}],
  "summary_for_user": "5 lines max"
}
```

### `openings/<ID>/status.json` (whoever acts on the opening)

```json
{"id": "JOB-...", "status": "analyzed",
 "history": [{"date": "2026-09-25T08:14", "status": "found", "by": "jobs-scout", "note": ""}]}
```

Statuses (`lowercase_snake_case`): `found`, `discarded`, `analyzed`, `in_preparation`, `in_review`, `not_approved`, `ready`, `delivered`, `applying`, `applied`, `manual_application`, `skipped`, `screening`, `interview`, `offer`, `rejected`, `closed`. Verdicts and results stay `UPPERCASE`: `filter` (PASS, FLAG, DISCARD), `fit.decision` (PURSUE, WATCH, REJECT), review `verdict` (APPROVED, FIX, HUMAN_REVIEW) and `submission.json` `result` (SUBMITTED, NEEDS_DATA, NOT_POSSIBLE).
Only one bot works on an opening at a time (the chain is linear), so there are no simultaneous writes.

### `outbox/ready/<ID>.json` (reviewer)

```json
{"id": "JOB-...", "type": "new | change", "company": "", "role": "", "work_mode": "", "score": 84,
 "apply_url": "", "files": ["/absolute/path/cv_ats.pdf"], "warnings": ["interview probably in English"]}
```

### `openings/<ID>/application/submission.json` (applier)

```json
{"id": "JOB-...", "result": "SUBMITTED | NEEDS_DATA | NOT_POSSIBLE",
 "method": "no_login_form | requires_account | email | linkedin | captcha | other",
 "filled_fields": [{"field": "", "source": "contact.yaml | application-data.yaml | answers.md | cv | consult:<card id>"}],
 "pending_questions": [], "screenshots": ["/path/before.png", "/path/confirmation.png"],
 "reason": "", "manual_kit": "application/kit.md"}
```

### `companies/<company>.md` (the analyst's subagent)

Profile with date, summary, product, sector, brand tone, team signals, news and sources. Reused while less than 30 days old.

### `tracking.csv` (regenerated by `deliver.py`; nobody edits it)

```text
id,date,company,role,url,source,filter,score,decision,status,applied_at,apply_method,notes
```

## 6. `{{ROOT}}/projects/jobs/AGENTS.md`

Merged after the base `AGENTS.md`. Copy as is, with the variables substituted. Include the `{{#confidential_search}}...{{/confidential_search}}` block only if that field is `true`:

```markdown
# Job search: squad rules

1. Every claim about {{name}} (experience, numbers, dates, tools, education,
   languages) must exist in achievements.yaml with verified: true and be cited by id. No
   achievement, no claim.
2. Never raise the proficiency level of an achievement: "participated" does not become "led",
   "familiar" does not become "expert". Never round a number up.
3. Languages: no document or answer claims a level higher than the one recorded in
   achievements.yaml.
4. jobs-profile.yaml, achievements.yaml, application-data.yaml, evidence/ and
   ../../user/ are read-only. If a piece of data is missing, block the task saying
   exactly what is missing.
5. Work only inside openings/<ID>/ of your task (and companies/ or outbox/ if your SOUL
   says so). Write your output following the contract in 02-architecture.md, update
   status.json and declare your files in kanban_complete.
6. Handoff: if your SOUL says so and your result justifies it, create the next bot's
   task with kanban_create: workspace dir:<absolute path of the opening>, idempotency-key
   <ID>-<stage>-<round>, and a body with the ID, stage, input and output paths, language and
   decisions made. Never create tasks for any other purpose.
7. Language of the documents for the company = language of the opening. Summaries for
   {{name}} in {{preferred_language}}.
8. Only jobs-applier submits applications, and only if its task body carries
   {{name}}'s explicit confirmation for that opening. Nobody else fills in external forms
   or writes to companies. Nobody creates accounts, logs in, pays or accepts terms other
   than those needed to apply and that {{name}} authorized.
9. Do not automate LinkedIn. If you are given a LinkedIn URL, look for the same opening on
   the company's website or ask for the text.
10. Contact and application data: only the writer (CV header) and the applier read
    them. Never in web searches or task comments.{{#confidential_search}} Do not
    search using {{name}}'s name, and do not mention their current employer outside the
    documents.{{/confidential_search}}
11. If the previous stage's file is missing or invalid, do not rebuild it: block and
    explain.
12. Direct consultation (base AGENTS.md rule) only for these pairs:
    jobs-writer → jobs-analyst: analysis or evidence questions (a requirement, the
    achievements that support it).
    jobs-applier → jobs-writer: the answer to a form question drawn from the application.
    jobs-reviewer → jobs-analyst: fit-analysis facts only, never about the documents
    under review.
    Record an assumption in the history note of status.json. Facts only {{name}} has
    (salary, authorization, availability) are never consulted: block with needs_input.
```

## 7. Direct consultation

A specialist missing one datum owned by another bot asks it directly with a support card and a dependency block, without going through the orchestrator. Protocol, card format, limits and deadlock rule: `base/02-architecture.md` §5.1. Allowed pairs (also in `squad.yaml` → `consult`):

| From | To | About | Answer comes from |
| --- | --- | --- | --- |
| `jobs-writer` | `jobs-analyst` | Analysis or evidence: why a requirement is must-have, which achievements support it | `analysis.json`, `companies/<company>.md`, `opening.md` |
| `jobs-applier` | `jobs-writer` | The answer to a form question not covered by `answers.md` | `application/`, `achievements.yaml` (verified only, cited by id) |
| `jobs-reviewer` | `jobs-analyst` | Fit-analysis facts only (must-have vs nice-to-have, hard gaps) | `analysis.json` |

The answering bot runs in CONSULT mode (`03-bots.md` §2). The reviewer never consults the writer: independence. The applier records a consulted answer in `submission.json` with source `consult:<card id>`. If the applier is not installed, its pair is dropped from `squad.yaml`.
