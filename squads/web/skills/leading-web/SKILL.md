# Leading the web squad

## When to Use

- The user starts a site, approves a spec, or asks for a change, a bug fix, a domain, a rollback or status.
- An `accept` card reaches you, or a card is blocked and needs a user decision.
- The `web-watch` cron reports a card in your Bot Chat, or in your messaging channel when one is connected.

## Procedure

0. **Base before any work.** Say in one line which folder and which git branch/worktree you are working from, before opening any app, tool or file. A repo with several branches keeps superseded direction that reads as current: old briefs, old pipeline docs, old launcher scripts for a discarded character or stack. Read the brief of the branch that holds the newest direction, list what the checkout still carries from the discarded direction, and ask the user to confirm the base before building on it. Never model, scaffold or configure against a branch the user has not named or confirmed. When the user says a previous direction is dead, asks to clean the repo or asks for a clean prompt to continue in a new session, follow `references/repo-handoff.md` (inventory, archive the evidence, rewrite the brief in place, safe branch deletion, self-contained handoff prompt).
1. **New site.** The site is the project this chat runs in; `<site>` is its primary folder (`desktop_project` `list` -> the active row; outside Desktop the `*` row of `hermes -p web project list`, or the folder the channel prompt names). No project: ask the user to create one with "+" in Sessions (pick web in the bottom selector), choosing its folder, and to open the chat inside it; when they name a folder instead, `tool_call` `desktop_project` `{"action": "create", "name": "<name>", "path": "<their folder>"}` (outside Desktop `hermes -p web project create "<name>" <folder>`). Never pick the folder yourself. Then run `python3 $HERMES_HOME/scripts/project_sync.py` so the workers get it. Set `site.yaml -> repo.path` (site-contract step 2), run the interview in `references/onboarding.md`, then write `<site>/site.yaml` and `<site>/decisions.md`. **When the site is the home of an existing app repo** (`<site>` already carries `package.json`, `AGENTS.md`, tests), that repo is the project and its own brief wins over anything the squad would scaffold: keep the squad's files at the repo root but outside its history (`printf '%s\n' site.yaml spec.md decisions.md inputs/ milestones/ reviews/ deploys/ >> .git/info/exclude`), so `git status` shows only real app changes and no builder mistakes the exclusion for a tracked file.
2. **Strict base and access, before any card.** Run site-contract `references/project-base.md` yourself, in this order and without asking: the base (`site_base.py --site <site folder>`, one command that reads `site.yaml`: the stack's official create CLI, packages through `pnpm add` with no version, strict TypeScript, the full quality gate, git hooks, first commit; it must end with `pnpm quality` green; when the JSON has `next`, fix the template code it names and run it again), then the access check (`web_access.py`): a login the user already has is reused; a missing CLI is installed; a missing login is started for them and opened as a tab. Then file the `onboarding` chain (`squad.yaml -> chains.onboarding`) per site-contract step 4, without `parents`, key `web:onboarding:<project>:init:repo`.
3. **Spec.** Research with `delegate_task` subagents (they run the cheap delegation model of this profile; never research on your own model): `inputs/`, the current site if any, and 2-3 reference sites with URL and date. A reference site the user names for its look or motion gets a real teardown before the spec is written — the stack with versions, the scene list in play order, the timing and audio mix as numbers — per `references/reference-site-teardown.md`; the spec asks builders to reproduce the method, never its models, audio or code. Write `spec.md` in the format of site-contract `references/file-formats.md` section 2, milestones per `references/onboarding.md` section 3. Run `official:software-development/grill-me` on it before the user sees it.
4. **Approve.** Send the plan message of `references/onboarding.md` section 4. Only the user's "ok" sets `status: approved` in `spec.md` and `active: true` in `site.yaml`.
5. **Milestone chain.** First put `<repo>` on the work item's branch (site-contract step 7). A TanStack site's first `api` card is its response headers in the Start server middleware (site-contract `references/project-base.md`). One card per stage of `squad.yaml -> chains.milestone`, in order, each with the previous card as `parents`, fields per site-contract step 4; skip `api` unless `site.yaml -> backend: true`. `run-id` = `m<n>-<scope-slug>`, or the work item id for a change or bug. A `ui` stage holding more than one deliverable (several assets, chapters, a shared look kit, sound) is split before filing: a contract card, one parallel card per deliverable, an integration card that the rest of the chain follows (`references/coordinating-builders.md`). File every card with the `kanban_create` tool, never `hermes kanban create` from the terminal: the tool subscribes this chat to its completion.
6. **Route models and specialists.** `web-backend` runs the `code-routine` lane by default. For architecture, auth, data-model or migration cards, pin the `code-complex` lane's model on the card at creation: the kanban card fields are `model` and `provider` (`hermes kanban create --model <model> --provider <provider>`; `provider` requires `model`), values from `local/installed.yaml -> lanes.code-complex`. File 3D, WebGL or complex-motion UI on `web-frontend-pro` (`skills: [building-3d-motion]`) only when the brief needs it; it is optional (`squadctl apply web --with web-frontend-pro`; with no squad CLI on the machine, confirm the profile in `local/installed.yaml` and file the card with `skills: [building-3d-motion]` directly) and `web-frontend` owns ordinary UI.
7. **Triage.** "change: ..." or "bug: ..." becomes a work item `<slug>-<YYYYMMDD>-<kind>-<nn>` in `spec.md -> Changes`, then a milestone chain with that id as `run-id`. A change to stack, provider or monthly cost needs a new spec approval first.
8. **Accept.** On your `accept` card: read the newest `reviews/<ID>-r<R>.json`, set the milestone note's `status: approved`, and `kanban_block(kind="needs_input", reason=<message>)` with the preview URL, the review's three `summary` lines and the reply options `publish`, `change: ...`, `bug: ...`, `rollback`; a board run cannot message the user, the block reaches your Bot Chat or messaging channel. On the reply, run step 7 or 9, then `kanban_complete(board: "web", task_id: <accept card>, summary: "<the reply>")`.
9. **Publish, rollback.** Ask one Yes/No question with `clarify`: what goes live, where, and the monthly cost. On a yes, put the `Confirmed:` line (site-contract Pitfalls) in the body and file one web-deployer card, `skills: [deploying-sites]`, stage `production` (chain `deploy-production`) or `rollback`, key `web:deploy-production:<project>:<run-id>:<stage>`. After the merge, `git -C <repo> switch main && git -C <repo> pull --ff-only` (site-contract step 7). Then copy `url`, `version_id` and the deploy time from the new `deploys/*-production-*.json` into `site.yaml -> production`.
10. **Domain.** File the same card with stage `domain` and no `Confirmed:` line. When the deployer blocks with the planned DNS records, show them to the user and ask Yes/No; post the yes as a `kanban_comment` with the `Confirmed:` line, then unblock (step 12).
11. **Status.** 3-5 lines per site from `site.yaml`, the milestone notes, the newest lines of `milestones/<ID>.progress.log` (what the builder saved and when) and `deploys/`: current milestone and status, last saved piece, last preview, live URL, what waits for the user.
12. **Live view, always on.** As soon as the base exists, and when the user asks for the site or says the tab is gone: `python3 "$HERMES_HOME/skills/squad-web/site-contract/scripts/live_view.py" start --repo <repo>` (reuses a running server); when the repo already owns its dev command (read `AGENTS.md` and `package.json`), start theirs instead — `live_view.py` serves a scaffold and the app needs its own env, secrets wrapper and port — with `terminal(background=true, persist_on_release=true)`, a `curl` health check on the port, and the port and command recorded in `<repo>/.hermes-live/server.json` before the tab opens. Then `tool_call` `desktop_preview` with `{"action": "open", "url": "<its url>", "label": "<site name>"}`. Do not reopen it on your own when the user comes back to the chat: the Desktop keeps a chat's tab, and the squad-hub plugin puts a lost one back; a reopen from you reloads the page. The site lives in that tab beside the chat and reloads on every file a builder saves; never show the site inline in the message or as a screenshot instead of the tab. Outside the Desktop app, send the URL and say it opens as a tab in the Desktop chat. `live_view.py stop` only when the user asks. While a 3D or offline-asset card runs, also open the renders board: `python3 "$HERMES_HOME/skills/squad-web/site-contract/scripts/live_renders.py" --site <site> --id <ID>` prints its path, then `desktop_preview` `{"action": "open", "url": "<that path>", "label": "<site name> renders"}`; it refreshes itself as the modellers overwrite their renders.
13. **Unblock.** For a card `web-watch` reports: `kanban_show` it, ask the user its question, post the literal answer with `kanban_comment`, then `kanban_unblock`. If the answer changes the spec, patch `spec.md` and show the change first.

## Pitfalls

- Before filing the first card of a long run, prove the workers can reach everything they need with real calls, not assumptions: list the project folder from a fresh shell (macOS privacy blocks `~/Documents`, `~/Desktop`, `~/Downloads` with `Operation not permitted` until Hermes.app and its bundled `python3` have Full Disk Access), run one Blender MCP scene call, and hit the dev server. A blocked folder makes every card crash twice and stall for hours while the user is away; fix access first, then file.

- One card = one deliverable a fresh worker can finish and save within 2-3 hours; never one builder for several chapters or assets. Split, contract and integrate per `references/coordinating-builders.md`; when a card runs over an hour with no saved piece, reclaim it, keep its unsaved files and split what is left.
- Every completion is shown the moment it lands, without waiting to be asked: the proof as a `MEDIA:` line, the live tab refreshed, which parts are still old, what runs next. Before any status reply, check `git log` and the board for pieces finished since the last message and show them first: a user who only sees stale states corrects work that has already changed.
- Never ask a non-technical user a technical question: decide with the defaults in `references/onboarding.md`.
- Never tell the user to install or log in to a tool, and never announce that you will "check how Cloudflare works": `web_access.py` checks, installs and starts the login; the user only approves the provider's page in the tab.
- Never pay, create accounts, buy domains, or delete repositories, zones or data.
- Never file a `ui` card before `spec.md` is approved. One work item per site at a time: no new chain while a card of the previous one is open.
- Never describe a reference scene you did not see on screen: a page whose WebGL context stalls keeps returning uniform dark frames with no error, so hash the captures, and when the renderer string says software GL capture it again in the system browser with a real GPU before writing the chapter table (`references/reference-site-teardown.md`).
- Never re-scaffold over an existing app repo: `site_base.py`'s create CLI is for a greenfield folder, and the gate for a repo that already builds is its own (`bun run quality`, per its `AGENTS.md`) — a second scaffold writes a rival template tree beside the app the user actually has.
- A dev server that dies at boot with a missing env var is not a broken project: start it the way the repo documents (its secrets wrapper such as `bun run dev:secrets`), never by inventing a `.env`, and never print the values it loads.
- A commit refused by the repo's pre-commit gate is not a no-op: hooks that format or restage leave files unstaged after the failure, and a quality or import-resolution failure usually means the checkout's `node_modules` still belongs to the previous branch. Run the branch's lockfile install, then `git status --short` and commit what is left before moving on (`references/repo-handoff.md`).
- Never start a GUI app or heavy tool (Blender, a browser profile, a dev server, a plugin install) without the one-line message that names what you are opening and why, before it opens: the user sees the window appear, never your intent, and reports it as unexplained background work.
- Never route an ordinary UI card to `web-frontend-pro`: it exists only for 3D, WebGL or complex motion. Pin the `code-complex` model on a `web-backend` card only for architecture, auth, data-model or migration work.

## Verification

- `spec.md` is `approved` and `site.yaml -> active: true` before the first milestone card exists.
- Before the first card: `pnpm -C <repo> quality` exits 0 and `web_access.py status` shows `gh` and the provider CLI logged in.
- Every card matches site-contract steps 4 and 5.
- User messages carry the preview URL and the reply options, never raw logs or file paths.
- `site.yaml -> production` matches the newest `deploys/*-production-*.json` with `ok: true`.
